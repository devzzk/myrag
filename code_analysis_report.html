关键问题

  • print() 泛滥：几乎所有模块都用 print() 代替 logging，输出格式不统一，无法控制级别。
  • API Key 泄露：BaseDashscopeProcessor.send_message 打印完整的 dashscope.api_key。
  • 硬编码路径：embedding_error.log、./temp/ 等写入工作目录，可能造成路径冲突。
  • logging.basicConfig 被多次调用（pipeline 多个方法），第二次调用无效果，导致早期设置可能被忽略。

重构风险矩阵：单文件修改而其他不动时最容易出问题的地方

高风险

1. 只改 prompts.py（不改 api_requests.py / reranking.py）

prompts.py 被 api_requests.py 和 reranking.py 同时引用（近循环）。如果:

  • 修改 Prompt Schema 类的字段名/类型（如 AnswerSchema.final_answer 从 Union[float,int,Literal['N/A']] 改类型），APIProcessor._build_rag_context_prompts 中选择 schema 时不会报语法错误，但 LLM 结构化输出将收到错误的 response_format，导致解析失败。
  • 修改 RephrasedQuestionsPrompt 的 instruction，下游 APIProcessor.get_rephrased_questions 的行为会发生变化，但无任何编译期警告。
  • 修改 RerankingPrompt 的 system prompt，LLMReranker 全部重排结果可能偏离预期，并且 dashscope 分支无法做结构化解析（当前硬编码默认分数 0.0）。
  • 修改 AnswerSchemaFixPrompt，所有 Provider 的 _reparse_response 修复失败率可能大幅上升。

2. 只改 api_requests.py（不改 tables_serialization.py / questions_processing.py）

api_requests.py 是"上帝模块"（5 个 Provider + Facade + Async），被多方依赖:

  • TableSerializer 继承 BaseOpenaiProcessor。如果修改 BaseOpenaiProcessor.send_message 的签名（增加必须参数），TableSerializer 继承同名方法但可能调用时缺少新参数。
  • APIProcessor.__init__ 的 Provider 调度使用 if/elif 链。如果增加新 Provider，QuestionsProcessor 和 pipeline.py 的 RunConfig 就必须同步更新 api_provider 的允许值，否则静默降级。
  • response_data 字典结构被 QuestionsProcessor 读取后存入 answer_details。修改字段名会导致审计日志中出现 None 值。
  • BaseDashscopeProcessor.send_message 打印完整 API Key（L681），这是一个安全隐患。

3. 只改 retrieval.py（不改 questions_processing.py）

  • VectorRetriever.retrieve_by_company_name 返回的 dict 结构（{"distance","page","text"}）被 QuestionsProcessor._format_retrieval_results 直接使用。如果增加/减少字段名，格式化的 RAG context 字符串可以编译通过但在 LLM 端产生错误上下文。
  • HybridRetriever 在内部实例化 LLMReranker（reranking.py）。如果修改了 LLMReranker.rerank_documents 的参数签名（如 llm_weight），HybridRetriever.retrieve_by_company_name 不会自动适配——因中间没有任何接口层。
  • _load_dbs 的文件结构校验逻辑（检查 metainfo / content / chunks）改动后，已有的 FAISS/JSON 目录可能全部不兼容。

4. 只改 pdf_parsing.py（不改 pipeline.py）

  • pipeline.py 直接暴力赋值 parser.metadata_lookup = ... 和 parser.debug_data_path = ...。如果将它们改为 property / 私有属性，pipeline 中的赋值立即报 AttributeError。
  • JsonReportProcessor 的 assemble_report 输出 JSON 结构被下游 4 个模块（parsed_reports_merging, text_splitter, ingestion, questions_processing）隐式依赖。修改该结构（如字段名）、则所有读取 JSON 的地方都需知道新结构，但目前没有任何 schema 校验。

中风险

5. 只改 pipeline.py（不改 main.py）

  • main.py 通过 from src.pipeline import Pipeline, configs, preprocess_configs 导入模块级配置字典。如果删除/重命名 configs 变量，main.py 的 CLI 命令 process_questions 报错。
  • if __name__ == "__main__" 内运行完整流程，修改该代码块的执行顺序会影响所有本地测试。

6. 只改 questions_processing.py（不改 retrieval.py / api_requests.py）

  • get_answer_for_company 创建 VectorRetriever / HybridRetriever 实例时传入 vector_db_dir 和 documents_dir，但不传入 embedding_provider。默认值是 "dashscope"。如果修改了 provider 选择逻辑（例如想统一用 openai embedding），但 VectorRetriever 的默认是 dashscope，就会出现不匹配。
  • _extract_companies_from_subset 的正则匹配逻辑与 subset.csv 的公司名格式强耦合。修改正则模式可能导致所有问题无法匹配到公司。
  • threading _lock 保护 answer_details，但 response_data 的赋值（L134）不在锁内——竞争条件。

7. 只改 tables_serialization.py（不改 api_requests.py）

  • 继承 BaseOpenaiProcessor，使用父类的 send_message、count_tokens。父类方法签名变化直接传导。
  • 全局 message_queue + TqdmLoggingHandler 模式：任何其他模块如果也使用 logging.Thread 并发可能导致消息混乱。

低风险

8. 只改 text_splitter.py / parsed_reports_merging.py

这两个模块没有其他 src.* 内部依赖，只被 pipeline.py 调用。但难点在于它们产出的中间 JSON 文件被下游隐式依赖：

  • 修改 TextSplitter.chunk_size 默认值（当前 300 tokens），分块粒度改变后向量库需重建。
  • 修改 PageTextPreparation._apply_formatting_rules 的渲染逻辑会影响所有下游读取 02_merged_reports 的模块。

9. 只改 ingestion.py

  • 独立模块，只被 pipeline.py 调用，内部依赖都来自外部库（faiss, dashscope, rank_bm25）。
  • 但 VectorDBIngestor.__init__ 中设置 dashscope.api_key，如果与 retrieval.py 中的设置发生冲突（先设置后覆盖），可能导致 API Key 错误。

10. 只改 api_request_parallel_processor.py

完全独立，无内部 src.* 依赖，只被 api_requests.AsyncOpenaiProcessor 调用。但签名修改会直接影响异步处理。

总结：最脆弱的 5 个痛点

  1. prompts.py 是"全局契约"：被两条路径引用（近循环），修改 Schema/Prompt 无编译期保护，LLM 输出可能静默失败。
  2. api_requests.py 是"上帝模块 + 紧耦合"：TableSerializer 继承 BaseOpenaiProcessor、QuestionsProcessor 依赖 APIProcessor 和 response_data，任何接口变更会级联。
  3. PDF 解析输出的 JSON 结构无 schema 校验：下游 4 个模块隐式假定相同的 JSON 字段名/结构，修改 pdf_parsing.py 的输出可能导致下游静默失败。
  4. dashscope.api_key 全局写 + 日志泄露：多个模块直接赋值给库的全局变量，且 BaseDashscopeProcessor.send_message 打印完整 API Key。
  5. pipeline.py 直接暴力赋值 parser 的内部属性（metadata_lookup、debug_data_path），PDFParser 类重构时必然破坏 pipeline.py。
