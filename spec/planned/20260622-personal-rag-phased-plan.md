# 个人 RAG 分阶段功能规划 Spec

> 状态：**planned** | 创建日期：2026-06-22

## 契约

本 spec 定义 `myrag` 作为个人知识库 RAG 系统的分阶段功能规划。系统以 `RAG-Challenge-2` 的处理链路为参考基线，保留其 `PDF 解析 -> 报告规整 -> 分块 -> 向量化 -> 检索 -> 问题处理` 的主流程，同时针对个人中文知识库场景进行改造，优先建立稳定的单用户知识问答闭环，再逐步增强检索质量、文档理解能力与任务路由能力。

### 参考基线与改造约束

1. 参考项目目录：`E:\language\python\src\zhihu\11-项目实战：企业知识库\RAG-Challenge-2-main`。
2. 参考项目保留的主流程包括：`parse_pdfs`、`process_reports`、`process_questions` 三段式处理。
3. 原项目中的 `Docling` 解析链路在本项目中替换为 `MinerU`。
4. 原项目中的 `OpenAI` API 调用在本项目中替换为 `DashScope`。
5. 默认问答模型使用 `qwen-turbo-latest`，默认向量模型使用 `text-embedding-v1`。
6. 初始知识库采用中文金融研报数据，目录约定为 `data/stock_data/pdf_reports/`。
7. 问题清单采用 `data/stock_data/question.json`，问题对象至少包含 `text` 与 `kind` 字段；开放式问题默认使用 `kind: "string"`。
8. 系统需要提供一个面向个人使用的前端入口，首选 `Streamlit`。

### 阶段一：MVP（可用闭环）

阶段目标：让用户能够导入个人文档，并基于可靠引用完成问答与摘要。

功能范围：

1. 单用户、本地优先的知识库使用模式。
2. 默认知识库目录采用 `data/stock_data/pdf_reports/`，以中文金融研报作为首批数据源。
3. 支持导入 `PDF`、`TXT`、`Markdown` 文档，优先保证 `PDF` 处理闭环。
4. 使用 `MinerU` 作为核心解析工具，对文本型 `PDF` 完成正文提取、基础清洗与结构化导出，替换参考项目中的 `Docling`。
5. 参照 `RAG-Challenge-2` 的主流程建立 `PDF 解析 -> 报告规整 -> Markdown 导出 -> 分块 -> 向量化` 的处理流水线。
6. 按段落、标题或固定窗口进行文档分块，并保留 `文件名`、`页码`、`标题路径` 等元数据。
7. 接入 `DashScope` 作为默认模型服务，使用 `qwen-turbo-latest` 作为问答模型，使用 `text-embedding-v1` 作为向量模型。
8. 完成文本向量化、向量存储与基础相似度检索。
9. 定义 `data/stock_data/question.json` 问题文件格式，问题对象至少包含 `text` 和 `kind` 字段，并支持开放式问题 `kind: "string"`。
10. 基于检索结果完成问答、摘要等基础生成任务。
11. 回答中附带引用来源，能够回溯到原文片段或页码。
12. 在未检索到足够依据时，系统明确拒答或提示知识库暂无相关内容。
13. 提供基础的 `Streamlit` 前端页面，用于文档导入、提问和结果展示。
14. 支持基础的文档删除、重新导入与索引重建。

### 阶段二：检索增强（效果提升）

阶段目标：提高召回率、排序质量与知识库可维护性。

功能范围：

1. 支持扫描版 `PDF` 的 `OCR` 解析。
2. 增加表格区域的识别、序列化与结构化提取能力，对齐参考项目的表格处理阶段。
3. 引入查询重写，结合多轮上下文补全用户问题。
4. 引入查询扩展，增强短问题和模糊问题的召回能力。
5. 支持混合检索，结合向量检索与 `BM25` 检索。
6. 支持父文档检索（parent document retrieval），提升引用页上下文完整性。
7. 引入 `Reranker` 对召回结果进行重排。
8. 支持按元数据过滤检索结果，例如按文件、标签、导入时间筛选。
9. 建立导入任务状态、失败重试、增量更新与去重机制。
10. 提供检索调试视图，展示召回片段、分数、重排结果与最终上下文。

### 阶段三：智能编排（能力扩展）

阶段目标：让系统能够根据任务类型自动选择处理链路，支持更复杂的个人知识工作流。

功能范围：

1. 增加意图识别，将用户请求区分为问答、摘要、信息抽取、闲聊等类型。
2. 根据不同意图切换不同的检索、提示词与生成策略。
3. 支持面向表格、章节、整篇文档的差异化处理链路。
4. 支持问题类型路由，覆盖 `boolean`、`string` 等不同 `kind` 的回答约束。
5. 支持多模型适配，允许切换本地或云端 `LLM` 与 `Embedding` 模型。
6. 支持多知识库或多集合路由，按主题选择检索范围。
7. 支持多文档比较问题处理，参考 `RAG-Challenge-2` 的多对象问题路由方式。
8. 保存多轮对话历史，并在需要时参与查询重写与上下文组装。
9. 提供回答质量反馈闭环，用于沉淀 bad case 与后续优化。
10. 提供可视化知识库管理能力，支持查看、编辑与维护文档元数据和切片结果。

## 验收标准

### 阶段一：MVP

- [ ] 用户可以成功导入至少一种文本型 `PDF`，并完成解析、切块、入库与索引建立。
- [ ] 系统支持通过 `MinerU` 完成至少一种文本型 `PDF` 的稳定解析，并输出可用于切块和引用的结构化结果。
- [ ] 系统默认通过 `DashScope` 完成问答与向量化配置，且默认模型配置为 `qwen-turbo-latest` 和 `text-embedding-v1`。
- [ ] 系统能够读取 `data/stock_data/question.json`，并正确处理包含 `text` 与 `kind` 字段的问题对象。
- [ ] 开放式问题能够以 `kind: "string"` 的格式进入问答主流程。
- [ ] 系统能够针对知识库内容回答问题，并在回答中提供可回溯的引用信息。
- [ ] 系统在无命中或低依据场景下不会编造答案，而是返回明确的提示。
- [ ] 系统提供一个可运行的 `Streamlit` 页面，至少支持提问与结果展示。
- [ ] 用户可以删除文档并触发对应索引清理或重建。
- [ ] 阶段一能力形成端到端可演示闭环。

### 阶段二：检索增强

- [ ] 扫描版 `PDF` 至少支持一种 `OCR` 处理路径并可纳入检索。
- [ ] 表格序列化或结构化提取能力能够进入后续分块和检索链路。
- [ ] 混合检索或重排中的至少一种增强策略落地，并可在典型问题上优于阶段一基线。
- [ ] 父文档检索、混合检索、重排三者中至少两项形成可组合配置。
- [ ] 查询重写在多轮问答场景下能够正确补全指代或省略信息。
- [ ] 知识库支持重复导入检测、增量更新或失败重试中的核心能力。
- [ ] 系统可以展示检索链路中的关键调试信息。

### 阶段三：智能编排

- [ ] 系统能够识别至少三类用户意图，并将其路由到不同处理链路。
- [ ] 系统能够基于问题 `kind` 对输出结构或回答策略进行区分。
- [ ] 多模型切换不破坏现有问答与检索主流程。
- [ ] 系统能够处理至少一种多文档或多对象比较类问题。
- [ ] 对话历史能够被持久化，并在需要时参与后续查询理解。
- [ ] 用户可以对回答结果进行反馈记录，供后续评估和优化使用。
- [ ] 知识库管理界面能够支持核心维护操作。

## 兼容影响

- 当前仓库尚未形成稳定对外接口，本 spec 仅定义功能规划，不引入立即生效的破坏性变更。
- 当前项目为独立新建项目，仅参考 `RAG-Challenge-2` 的流程设计；`MinerU` 与 `DashScope` 作为默认方案，需要在实现阶段统一配置层与输出格式。
- 若问题文件从通用问答转为 `text + kind` 结构，现有问答入口需统一适配问题类型字段。
- 阶段二若引入新的索引结构、元数据字段或 `OCR` 流程，可能要求执行历史数据重建。
- 阶段三若增加意图路由与多模型适配，需要保证阶段一问答主链路仍可作为默认回退路径。
